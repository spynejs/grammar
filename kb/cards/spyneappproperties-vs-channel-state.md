### spyneappproperties-vs-channel-state
`op:spyneappproperties-vs-channel-state` · standard · CHOOSE

Placement judgment for a value — three homes, decided by tests in order. TEST 1 — OWNERSHIP/DURABILITY (the gate for view-local): if no other view or consumer needs the value AND it dies with the view, it is view-local (props / held state, computed by trait methods) — never a channel, never SpyneAppProperties; its externally meaningful RESULT still transmits through a channel. Either failure forces the value out of the view for a different reason: shared → it must be findable (view-internal state is invisible to outsiders); outlives the view → it must be held by a longer lifetime. TEST 2 — CHANGE (for values that survive test 1, i.e. shared or durable): if it changes and anything renders from it → Channel state. If it does not change within the app session (user name, email, config) → SpyneAppProperties setProp/getProp (isTemp=true = read-once-then-removed: one-shot handoffs and handshake tokens — see handshake-via-temp-prop). Static means not expected to change within the session: a live-editable profile field is changing state even if the field is 'user name'. DELIVERY-ENVELOPE EXCEPTION: when a legitimate consumer must read a changing value outside the channel's delivery envelope — too EARLY (a constructor-time gate, before any subscription can exist: 'am I signed in') or too OFTEN (a hot-path reader outpacing emission: a WebGL-style consumer reading a live DOM attribute per frame) — SpyneAppProperties is the sanctioned readable surface for that constrained consumer. Guardrails: exactly one writer; the channel remains the semantic authority — sync-read case: changes still announce through the channel so reactive consumers subscribe rather than poll; hot-path case: discrete meaningful transitions still announce (see discretize-continuous-input-at-source) while the continuous value rides SpyneAppProperties; and consumers that CAN subscribe still subscribe — the SpyneAppProperties read belongs to the constrained consumer only, never a general convenience alternative. CONSTANTS CLAUSE: constants live on SpyneAppProperties — never in scattered per-feature constants files. Findability by bounded surface area: one canonical home makes locating any constant intuitive; indiscriminate constants files make it forensic.

**Prior override:** Two naive priors, both too broad: a module-level singleton/global/context object for anything app-wide, and 'state belongs in a Channel' for anything that changes. Durable, shared, or independently meaningful state belongs in a Channel; disposable presentation state does not earn one merely because it changes over time — and one view's private scratch earns neither home.

**Specimens (both branches):** _[from whyBlocks — bracket pointers]_

- Specimen: server-tests-constants.js DELETED in the optimistic-matrix refactor; its contents moved to SpyneAppProperties. The naive per-feature constants.js prior is universal and is exactly how findability dies by a thousand cuts.
- Ephemeral specimen (Acme pagination): currentPageIndex — derived from matchedIds + itemsPerPage, reset by a new match set, read by no other view, meaningless once the paginator disposes. View-local was correct; the initial channel placement was the naive 'it's called state' prior. Its result (visibleIds) transmits through the channel.
- Sync-read specimen (Acme auth): session state is CHANGING state, so the channel is its semantic authority — ChannelAcmeAuth is the single writer and announces transitions; SpyneAppProperties carries the current value as the readable surface for constructor-time gates.
- Hot-path specimen: a WebGL-style consumer reading a changing DOM attribute per frame — emission cannot serve a per-frame reader. The raw value rides SpyneAppProperties for that consumer; threshold/state transitions still announce through the channel (discretize-continuous-input-at-source arriving from the other direction).
